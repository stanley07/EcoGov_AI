# WF-2 Database Model

Status: Approved with required review changes incorporated

## Conventions

- UUID primary keys; UTC `TIMESTAMPTZ`; database time authoritative.
- Tenant-owned tables have `UNIQUE (tenant_id, id)` and tenant-leading indexes. Every parent/child reference carries `tenant_id`; single-column UUID foreign keys are forbidden for tenant-owned notification relationships.
- Organization references use `(tenant_id, organization_id)` composite foreign keys.
- Mutable aggregates have positive `version` for compare-and-set updates.
- Published content and status history are append-only/immutable through restricted triggers.
- JSON is schema-versioned, size-bounded, and used only where relational columns cannot express the contract safely.
- Secrets and unrestricted message bodies are stored as encrypted envelopes or secret/object references, never plaintext columns.

## Mandatory composite foreign-key matrix

Migration 34 must create every applicable `UNIQUE (tenant_id,id)` parent key and the following composite references; a single-column UUID FK is not an acceptable substitute:

- recipient -> request, user, organization;
- destination -> recipient;
- delivery -> request, recipient, destination, provider route, and `task_execution`;
- attempt -> delivery;
- status history -> request and, when present, delivery, attempt, task, and outbox event;
- channel policy -> organization, provider route, and quiet-hours policy;
- user preference -> user, organization, and quiet-hours policy;
- suppression -> user/organization when present;
- route and route entry -> organization/route;
- webhook endpoint -> organization; challenge -> endpoint; callback -> endpoint/delivery;
- deduplication record -> request/delivery when present;
- inbox item -> organization, user, request, and delivery;
- replay request `(tenant_id,parent_request_id)` -> request `(tenant_id,id)`.

Migration 34 may add `UNIQUE (tenant_id,id)` to reused `task_execution` and `outbox_event` only after preflight proves it is absent and every new notification FK uses it. Global provider/catalog parents use their explicit global ownership keys; tenant-owned children may reference them only through the constrained tenant-local binding/route relationship. Nullable catalog tenant qualifiers use `MATCH FULL` and `UNIQUE NULLS NOT DISTINCT` semantics so partial-null composite references are impossible.

Template binding rotation must lock the binding and candidate version, verify the candidate is `published`, verify its template owns the exact `(application_key,semantic_key)` being rotated, enforce tenant/catalog ownership compatibility, and then rotate the single default atomically. Service validation and database constraints/triggers both enforce this invariant.

## Required indexes

- Claimable delivery: `(state,next_attempt_at,priority,created_at)` partial for `queued/scheduled/transient_failed/rate_limited`.
- Request browse: `(tenant_id,organization_id,created_at DESC,id)`.
- Inbox: `(tenant_id,user_id,state,created_at DESC,id)`.
- Attempts: `(tenant_id,delivery_id,sequence_number)`.
- Status history: `(tenant_id,request_id,sequence_number)`.
- Webhook callback replay: `(provider_id,nonce,timestamp)` plus expiry maintenance.
- Suppression lookup: `(tenant_id,channel,destination_digest,starts_at,expires_at)`.
- Recipient role/org resolution relies on existing tenant-leading membership indexes; migration preflight must prove them.
- Rate-limit buckets use daily range partitions on `window_start`, tenant-leading active-window indexes, and no unbounded per-destination index containing raw PII.

## Rate-limit partitioning and cleanup

Transient PostgreSQL rate state uses a token-bucket or sliding-window algorithm, never a fixed-window reset that permits boundary bursts, and is partitioned daily by `window_start`. Only current and immediately preceding partitions remain attached to latency-sensitive indexes. A leased/fenced maintenance task creates future partitions and drops expired partitions after the default 7-day operational retention (or a shorter reviewed tenant/provider policy). Aggregated, non-PII rate metrics may be retained for 90 days in the metrics system, not in transient buckets. Cleanup is idempotent, tenant-neutral, bounded, audited by partition/count metadata, and alerts before partition creation or deletion failure can affect sends. High-cardinality per-user/destination buckets may use an approved cache, but PostgreSQL remains the fail-closed authoritative fallback for regulated limits.

## Retention and deletion

- Templates, request headers, attempts, state history, and audit follow regulated evidence retention.
- Message content/destination envelopes use shorter classification-specific retention and cryptographic erasure where legally permitted.
- Inbox archival is not audit deletion.
- Legal hold overrides scheduled purge and is itself audited.
- Tenant deletion remains a governed lifecycle; foreign keys use `RESTRICT`, not cascading evidence loss.
